# 完整调试演示数据设计

## 背景

测试环境通过 `deploy/scripts/reset-test-db.sh` 重建数据库、执行全部迁移，并传入 `--seed-demo` 导入 `backend/scripts/seed_demo_data.sql`。当前演示种子已经包含用户、商家、少量供需、权益、审核记录、指标、消息和拿货地图数据，但无法稳定支撑当前完整业务调试：

- 公开供需只有少数类型，无法逐项验证现有供需类型、方向筛选和详情字段。
- 招聘入口已经在冷启动阶段下线，但演示种子仍创建公开招聘信息，可能出现在首页和公开列表。
- 供需状态只覆盖 `published`、`pending`、`rejected`、`expired`，缺少草稿、人工审核、审核重试和下架等管理分支。
- `resources` 的种子插入遗漏必填字段 `resource_type_config_version` 和 `resource_type_snapshot`，与当前数据库结构不兼容；全新数据库导入时会触发非空约束错误。
- 静态校验主要检查 SQL 是否包含若干字符串，无法证明全部类型、方向和状态矩阵已经覆盖，也无法发现资源配置快照缺失。

本次目标是把演示种子完善为可重复执行的完整供需调试集，让开发者执行测试库重置脚本后即可调试首页、市场、搜索、详情、商家主页、我的发布、审核和生命周期状态。

## 目标

1. 全新数据库执行全部迁移后，可以一次性成功导入演示种子。
2. 当前启用的 26 个供需类型各有至少 1 条有效公开样例。
3. 当前可见的 7 个供需一级类目均有公开数据，首页“近期供需”和供需市场重置后不为空。
4. 启用的 6 个需求方向类型均有公开样例；已停用的求职类型仅保留历史非公开样例。
5. 招聘、求职两个已停用类型不进入首页、搜索和公开供需列表。
6. 覆盖 `draft`、`pending`、`manual_review`、`audit_retry`、`published`、`rejected`、`taken_down`、`expired` 八种资源状态。
7. 额外覆盖置顶、即将过期、近期成交和超过公开保留期的成交数据。
8. 列表摘要、详情规格、类型名称、方向、搜索文本和标签均使用真实业务字段。
9. 已认证和未认证商家均有可验证数据，商家主页能展示多条不同类型的供需。
10. 审核记录、资源指标、联系事件和消息与资源状态保持一致。
11. 静态校验可以准确发现类型、方向、状态或配置快照覆盖退化。
12. 种子保持幂等，重复导入不会产生重复主数据或破坏关联关系。

## 非目标

1. 不改变数据库表结构或新增迁移。
2. 不修改公开 API、管理后台 API 或小程序页面行为。
3. 不为支付、短信、微信内容审核、七牛上传等外部依赖伪造可实际调用的凭据。
4. 不覆盖项目所有商业化边界；本次只维护与供需展示和管理直接相关的权益数据。
5. 不自动执行远程测试库重置，也不覆盖用户现有远程数据。
6. 不为每条资源配置真实远程图片；只保留有图和无图两类可控展示分支，避免演示数据依赖不稳定的第三方图片服务。

## 方案选择

采用“单文件显式场景矩阵”方案：继续以 `backend/scripts/seed_demo_data.sql` 作为唯一演示种子，为每个供需类型编写可读、真实的业务样例，并通过 `backend/scripts/validate_demo_seed.mjs` 校验覆盖矩阵。

选择理由：

- 显式数据可以直接看出每条资源用于调试什么场景，出现页面问题时容易定位。
- 每个类型可以使用自己的真实字段名和合理字段值，能够验证配置驱动详情，而不是只验证数据库插入。
- 保持单文件可以直接复用现有 `update-test-db.sh --seed-demo` 流程，不引入新的执行顺序和打包逻辑。
- 通过集中校验常量维护预期类型和状态，能够在供需配置变化时明确提示演示数据需要同步更新。

不采用按配置自动生成通用资源。自动生成虽然 SQL 更短，但标题、属性和摘要缺少业务真实性，容易掩盖某个类型字段映射错误。

不采用按领域拆分多个 SQL 文件。本次种子规模仍可由单文件维护，拆分会额外改造打包、执行顺序和事务边界，偏离本次目标。

## 数据角色设计

保留现有稳定演示 ID，并在同一 ID 段扩展角色。用户和商家名称明确标注业务身份，便于登录或在管理后台搜索。

演示角色至少包括：

1. 童装工厂：发布工厂直批、承接加工和厂房类供给，已认证。
2. 库存批发商：发布尾货、库存出售、二手转让等供给，已认证。
3. 面辅料供应商：发布面料和辅料供给，已认证。
4. 房产与场地服务商：发布商铺、住宅、公寓、厂房和仓库供给，已认证。
5. 本地综合服务商：发布样衣租赁、维修、搬家保洁、培训等本地服务，已认证。
6. 采购商：发布童装求购、招加工厂、场地求租和二手求购，未认证，用于验证需求方向和未认证展示。

每个需要进入“我的发布”的商家都具有激活的管理员绑定；采购商也绑定独立演示用户，避免只能查看公开数据而不能调试需求管理。

## 生命周期场景设计

除每个启用类型的公开基准数据外，增加以下专用状态样例：

- `draft`：商家尚未提交的草稿。
- `pending`：已提交并等待自动或人工审核。
- `manual_review`：内容审核转人工处理。
- `audit_retry`：外部内容审核暂时失败，等待后台重试。
- `rejected`：资料不完整并包含明确驳回原因。
- `taken_down`：商家主动下架并包含下架原因和下架时间。
- `expired`：超过有效期的历史资源。
- 即将过期：仍为 `published`，有效期为重置时间后 1 天。
- 近期成交：仍在成交后 7 天公开保留期内。
- 历史成交：成交时间超过 7 天，不应出现在公开列表。
- 置顶：`top_started_at` 已开始且 `top_expires_at` 未结束，应排在普通资源前。

审核记录只为实际发生审核决策的资源创建。草稿不创建审核记录；待审核和审核重试可以保留待处理状态，不伪造审核通过记录；驳回和公开资源分别记录对应审核动作。

## 资源配置快照

每条资源必须写入：

- `resource_type_config_id = rtc.id`
- `resource_type_config_version = rtc.version`
- `resource_type_snapshot`
- `type_code = rtc.type_code`
- `direction = rtc.direction`

`resource_type_snapshot` 在插入时使用对应 `resource_type_configs` 行构建，字段与业务创建逻辑保持一致：

- `version`
- `typeCode`
- `typeName`
- `direction`
- `fieldSchema`
- `requiredFields`
- `filterFields`
- `displayTemplate`
- `reviewRules`
- `sortWeights`
- `messageRules`
- `commercialRules`
- `defaultValidDays`

这样可以保证列表 `typeName`、详情字段结构、商业规则和历史配置语义完整。发生冲突更新时，配置 ID、版本、快照、方向和全部展示字段都必须同步，确保重复导入后不会保留旧快照。

## 字段与展示数据规则

1. `attributes` 使用该类型 `field_schema` 中定义的真实 key。
2. `category`、`price_text`、`quantity_text` 与 `display_template.summary` 指向的属性保持一致。
3. 标题包含可搜索的业务关键词，例如“卫衣”“尾货”“小单快反”“仓库”“求租”。
4. 标签同时覆盖常用搜索场景和不同标签数量，但不写入手机号等敏感信息。
5. 联系方式只使用固定演示号码和演示微信号。
6. 时间均相对 `now()` 或 `current_date` 生成，重置后不会立即全部过期。
7. 少量有图样例使用小程序包内已经存在的 `/static/home/factory-hero.jpg`，其余资源保留空图，分别验证有图卡片和无图兜底，不依赖第三方图片服务。
8. `is_verified` 与商家认证状态保持合理关系，但仍保留未认证需求样例。

## 关联数据

### 审核与管理

- 为公开、驳回、下架和过期资源创建符合状态的 `resource_review_records`。
- 操作日志覆盖商家认证、资源通过和资源驳回等典型后台动作。
- 消息至少包含审核通过、审核驳回和即将过期三类。

### 指标与联系

- 供给和需求资源都具有 `resource_metrics_daily` 样例。
- 指标包含曝光、搜索曝光、列表曝光、详情、电话、微信和分享。
- 联系事件关联真实演示用户、资源和商家。
- 指标和事件使用固定 ID 或唯一约束 upsert，重复导入不累加。

### 权益

- 已认证商家具有发布额度和刷新额度。
- 至少一个商家具有可用置顶券。
- 置顶资源的时间状态与权益调试数据相互独立，避免导入时实际消耗权益。

### 地图

现有拿货地图演示数据保持不变，只在商家角色扩展导致关联需要同步时做精准调整。本次不扩展地图对象数量。

## 幂等与事务

演示种子继续在单个 `BEGIN`/`COMMIT` 事务内执行。任何语句失败时，本次导入整体回滚，避免出现用户已写入但资源未写入的半成品状态。

主数据使用固定 TSID 和 `ON CONFLICT`：

- 冲突更新必须恢复演示数据预期状态，包括商家激活状态、资源状态、时间、快照和关联字段。
- 多对多或自然唯一关系优先使用现有唯一约束避免重复。
- 指标按资源和日期更新，不在重复执行时累加。
- 审核记录使用固定 ID，重复执行时更新为当前设计内容或保持唯一。

## 校验设计

`backend/scripts/validate_demo_seed.mjs` 从简单字符串检查升级为结构化静态校验，至少验证：

1. 28 个类型代码均出现在资源场景矩阵中。
2. 26 个启用类型均有 `published` 场景。
3. 招聘和求职没有 `published` 场景。
4. 7 个需求类型均有场景，其中 6 个启用需求类型公开，求职为非公开历史状态。
5. 八种资源状态均被覆盖。
6. SQL 明确写入并冲突更新 `resource_type_config_version` 和 `resource_type_snapshot`。
7. 快照包含所有约定配置字段。
8. 公开、置顶、即将过期、近期成交和历史成交场景标识齐全。
9. 不重新引入已下线的独立采购需求或人工撮合表。
10. 演示 ID 不截断、不重复，关键关联 ID 存在。

重置脚本原有校验继续保留，用于验证迁移后的配置总数、一级类目和需求方向配置。

## 验证流程

实现完成后按以下顺序验证：

1. 运行 `node backend/scripts/validate_demo_seed.mjs`，验证种子矩阵。
2. 运行 `node --test backend/scripts/validate_migrations.test.mjs deploy/scripts/update-test-db.test.mjs deploy/scripts/reset-test-db.test.mjs`，验证迁移和重置流程没有退化。
3. 在临时 PostgreSQL 数据库执行全部 `*.up.sql`，再执行 `seed_demo_data.sql`。
4. 查询各类型、方向和状态数量，确认与设计矩阵一致。
5. 使用当前后端访问首页资源和公开资源接口，确认：
   - 首页和公开列表非空。
   - 26 个启用类型均可按类型筛选。
   - 6 个启用需求类型均可按需求方向筛选。
   - 招聘、求职和其他非公开状态不会出现在公开结果。
   - 置顶资源排序优先。
   - 历史成交资源不公开。
6. 重复执行一次种子，确认数量不增长且关联数据保持一致。

如果本地缺少可用 PostgreSQL，则完成全部静态和脚本测试，并明确把真实数据库导入验证留给测试环境重置执行；不得把未实际运行的数据库验证描述为已通过。

## 完成标准

满足以下条件后视为完成：

- 种子数据与当前数据库约束兼容。
- 类型、方向、状态和特殊生命周期矩阵全部通过自动校验。
- 当前启用供需类型的公开调试数据完整。
- 已停用招聘类型不会污染公开页面。
- 资源配置快照完整且可重复更新。
- 关联审核、指标、联系、消息和权益数据不存在悬空引用。
- 现有迁移、演示种子和重置脚本测试全部通过。
- 未修改与测试数据无关的业务代码。
