# 微信小程序按钮网络请求加载反馈设计

## 1. 背景与目标

当前 `wxapp` 的网络请求反馈由各页面自行维护，存在以下不一致：部分按钮有禁用和状态文案，少量按钮使用微信原生 loading，部分关键写操作没有可见反馈或防重复提交。用户在弱网环境下可能无法判断点击是否生效，并可能重复发起发布、保存、关注、刷新、下架或删除等请求。

本次改动目标是统一“用户点击后需要等待服务端结果”的交互反馈，同时保持改动精准，不改变业务接口、请求协议和页面视觉结构。

验收标准：

1. 前台业务请求开始后，触发按钮立即显示与操作匹配的 loading，并进入禁用状态。
2. 同一操作未结束前再次点击不会重复发起请求。
3. 成功、失败或用户取消支付后，loading 均能可靠恢复。
4. 列表内操作只锁定当前记录或当前操作，不无故锁定整个页面。
5. 后台统计、曝光、已读上报等非阻塞请求不显示 loading，不拖慢跳转。
6. 原有成功提示、错误提示、确认弹窗和支付流程保持有效。

## 2. 方案选择

### 2.1 采用方案：页面局部业务状态

每个页面或组件维护与业务动作对应的状态，例如：

- 单一表单使用 `submitting`、`savingDraft`。
- 列表行操作使用 `busyResourceId` 与 `busyAction`，只影响被操作的记录。
- 联系方式使用 `contactAction`，区分电话与微信。
- 关注、收藏等单按钮操作使用独立布尔状态。

模板统一绑定微信小程序按钮原生 `loading`、`disabled` 和动作状态文案。状态从真正开始访问服务端时设置，在覆盖完整异步链路的 `finally` 中恢复。

采用该方案的原因：状态与用户动作一一对应，能够处理并行请求和列表局部操作，也不会影响页面生命周期请求及后台请求。

### 2.2 不采用：公共请求层默认全局 loading

不在 `wxapp/api/request.js` 中为所有请求自动调用 `uni.showLoading`。页面初始化、并发加载、下拉刷新、曝光统计和后台记录共用该请求层，强制全局 loading 会产生闪烁、遮挡、多个请求相互提前关闭 loading 等问题。

### 2.3 不采用：仅显示提示文字

只修改按钮文字而不绑定 `loading` 和 `disabled`，不能形成统一的动态反馈，也无法可靠避免重复提交。因此业务按钮需要同时具备动画、禁用和动作文本。

## 3. 交互规则

### 3.1 必须显示按钮级 loading

以下由用户主动触发、且必须等待服务端结果的操作需要按钮级 loading：

- 登录、注销账号。
- 发布供需、保存草稿、上传并保存商家资料。
- 关注商家、收藏或取消收藏供需。
- 我的发布中的刷新、置顶、下架、再发类似、删除。
- 供需详情管理中的刷新、置顶、下架、再发类似、删除。
- 查看电话、复制微信所需的联系方式查询、权限校验、订单创建及支付链路。
- VIP、次数包和置顶服务购买。
- 档口候选搜索、档口绑定、地图位置纠错和问题举报。
- 用户明确点击的搜索、刷新、重新加载和加载更多。

确认型操作在用户确认弹窗后才进入 loading；用户取消确认时不显示 loading。

### 3.2 使用页面或列表级 loading

分类切换、筛选标签、下拉刷新、上拉分页等操作继续使用现有页面或列表加载状态。显式“搜索”“刷新”“重新加载”按钮同时绑定该状态的原生 loading；筛选标签本身不逐个显示旋转动画。

页面已有数据时，刷新不清空旧内容；加载状态在原内容上反馈，避免弱网时页面闪空。

### 3.3 不显示 loading 的请求

以下请求属于后台记录或不应阻塞主流程，不增加按钮 loading：

- 资源曝光、详情浏览、分享和商家主页点击统计。
- 消息已读上报；失败仍保持现有友好提示，但不延迟目标页面跳转。
- 页面预加载、低优先级辅助数据加载。

若当前实现为了等待后台记录而延迟跳转，本次只在与 loading 改动直接相关且有现有测试保护时调整为非阻塞；不扩展为独立埋点重构。

## 4. 状态与数据流

标准业务按钮流程：

1. 执行本地登录和表单校验。
2. 如有风险操作，展示确认弹窗。
3. 检查当前动作是否已处于忙碌状态，忙碌时直接返回。
4. 设置动作状态，按钮显示原生 loading、动作中文文案并禁用。
5. 执行上传、业务请求、支付和结果刷新等完整链路。
6. 保留现有成功提示；失败时使用请求层或页面已有的友好中文错误提示。
7. 在 `finally` 中恢复动作状态。

对于同一个按钮可能执行多段服务端请求的流程，loading 必须覆盖整条链路。例如发布包含图片上传、草稿更新和提交审核；置顶包含权益查询、订单创建、支付和结果刷新。

对于列表行操作，状态至少包含资源 ID；同一时刻只允许一个高风险资源动作，避免列表刷新与多条写操作相互覆盖。未被操作的记录保持可浏览，是否允许发起第二条写操作以现有页面数据一致性为准，本次统一为不允许并行写操作。

## 5. 页面改动范围

### 5.1 高优先级写操作

- `wxapp/components/ResourcePublishForm.vue`：发布和保存草稿使用互斥状态，上传期间同步禁用图片增删与两个提交按钮。
- `wxapp/pages/my-resources/index.vue`：刷新、置顶、下架、再发类似、删除使用资源级动作状态。
- `wxapp/pages/resource/detail.vue`：管理动作、收藏、电话和微信使用可见状态；已有 `managementBusy` 扩展为带动作名称的状态。
- `wxapp/pages/merchant/detail.vue`：关注按钮增加 loading 和重复点击保护。

### 5.2 已有状态但反馈不完整

- `wxapp/pages/login/index.vue`、`wxapp/pages/account/settings.vue`、`wxapp/pages/resource/report.vue`、`wxapp/pages/vip/index.vue`：复用现有状态补充原生 `loading`。
- `wxapp/pages/merchant/profile.vue`：保存按钮复用 `submitting`，显示原生 loading 和“保存中”文案；保留微信手机号已有 loading。
- `wxapp/pages/merchant/map-binding.vue`：候选搜索和绑定按钮复用现有状态，补充动画和状态文案。
- `wxapp/pages/publish/index.vue`：类目刷新复用 `loadingCategories`。
- `wxapp/pages/sourcing-map/index.vue`、`wxapp/pages/sourcing-map/legacy-canvas.vue`、`wxapp/pages/search/index.vue`：显式搜索、刷新、重试按钮复用已有列表状态。
- `wxapp/components/ResourceList.vue`：加载更多按钮复用 `loading` 展示原生动画。

不为了本次需求创建全局状态库或通用请求装饰器；只有出现真实重复且不会隐藏业务语义时才提取小型辅助函数。

## 6. 文案规则

按钮忙碌文案使用明确的进行时：

- `登录中`、`保存中`、`提交中`、`搜索中`、`刷新中`。
- `关注中`、`取消关注中`、`收藏中`、`取消收藏中`。
- `置顶中`、`下架中`、`删除中`、`准备中`。
- `查询中`、`解锁中`、`购买中`、`支付处理中`。

错误消息继续使用现有请求层和页面的中文友好文案，不把原始服务端错误、支付参数或内部字段暴露给用户。

## 7. 异常与边界处理

- 所有状态必须在 `finally` 中恢复，不能只在成功分支恢复。
- 页面跳转成功前可保持 loading；页面未跳转或支付取消时必须恢复。
- 原生支付弹窗打开后仍保持对应按钮忙碌，直到支付结果和权益刷新完成。
- 表单校验失败、未登录、用户取消确认时不进入 loading。
- 已经处于忙碌状态的处理函数直接返回，模板禁用不是唯一的防重复措施。
- 请求失败时不清空用户已填写的发布、资料和举报内容。
- 不为 `uni.chooseImage`、`uni.chooseLocation`、`uni.makePhoneCall` 等纯原生交互单独显示服务端 loading；只有其内部实际发起服务端请求时显示。

## 8. 测试与验证

采用现有 Node 测试约定，通过读取 Vue 源码和必要的纯函数行为验证以下合同：

1. 关键按钮同时绑定 `loading` 与 `disabled`。
2. 处理函数包含忙碌状态短路和 `try/finally` 恢复。
3. 发布和保存草稿互斥，防止创建重复供需。
4. 列表资源动作只展示当前资源、当前动作的 loading。
5. 后台统计入口未被错误地增加阻塞 loading。
6. 现有页面流程、接口合同和构建不回退。

先编写失败测试并确认失败原因，再实施最小改动使其通过。最终执行 `npm test`、页面/流程校验和微信小程序构建；如完整 `npm run check` 受环境限制，明确记录未完成项及原因。

## 9. 非目标

- 不修改后端接口、数据库或 API 返回结构。
- 不重做页面视觉设计，不引入新的 UI 组件库。
- 不给所有页面初始化请求增加全屏 loading。
- 不在本次改动中重构完整埋点、消息或支付架构。
- 不改变现有成功跳转、确认规则和业务权限判断。
