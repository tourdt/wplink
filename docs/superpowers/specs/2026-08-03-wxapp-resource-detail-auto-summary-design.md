# 供需详情自动摘要布局设计

## 背景与目标

小程序发布供需时不要求商家手动填写标题。发布端会根据二级类型、分类摘要、数量摘要和价格摘要自动生成标题，并将这些摘要字段写入资源记录。当前详情页虽然已拿到这些数据，但首屏只展示图片和描述，用户需要继续浏览才能判断是否匹配。

本次仅实施详情页前端布局优化，不新增发布字段，不修改资源类型配置，不调整后端接口。目标是在不增加发布负担的前提下，让访客在首屏快速判断供需方向、具体类型、核心交易条件和是否需要联系。

## 范围

### 包含

1. 在详情首屏展示供需方向、二级类型、自动生成标题、价格/预算与数量/面积摘要。
2. 调整详情内容顺序为：图片或无图封面、首屏摘要、补充说明、详细参数、地址、商家资料、同类推荐、弱化的交易提醒。
3. 将所有面向用户的“供应”固定文案改为基于 `direction` 的动态文案。
4. 根据字段内容长度决定参数项是否占满整行，避免地址、交期、服务范围等内容在双列布局中拥挤。
5. 无图资源展示与有图资源一致的业务摘要，不再仅显示泛化占位文案。
6. 更新资源详情页的前端回归测试。

### 不包含

1. 不新增手动标题输入框。
2. 不修改 `resource_type_configs` 的 `displayTemplate`。
3. 不增加后端 `summaryItems` 接口字段。
4. 不改变联系方式付费解锁、收藏、举报、商家资料准入或相关推荐查询规则。
5. 不修改数据库结构或迁移。

## 页面结构

```text
图片 / 无图封面
供 / 求标签 · 二级类型
自动摘要标题
价格/预算 ｜ 数量/面积

补充说明
详细参数
地址与导航
商家资料入口
同类推荐
交易提醒

更多 ｜ 微信 ｜ 拨打电话
```

首屏摘要使用已存在的 `title`、`typeName`、`direction`、`priceText`、`quantityText`。其中 `title` 是发布端自动生成的业务摘要，不向用户暗示其为手工填写标题。

## 前端设计

### 首屏摘要

- 图片存在时，摘要卡紧接图片展示；无图时，摘要位于信息封面内部。
- 供给使用“供应”，需求使用“需求”；二级类型优先使用服务端返回的 `typeName`。
- 标题为空时，依次回退到“分类 + 数量 + 价格”组合和类型名称。
- 价格/预算、数量/面积仅在有值时展示；不显示“待沟通”“面议”等人为占位。
- 用户填写的 `description` 使用“补充说明”分区展示；描述为空时不展示虚构说明。

### 参数与内容顺序

- 短值参数保留双列布局。
- 值超过 12 个字符、包含换行，或标签属于地址、区域、交期、服务范围、工艺要求、备注时，参数项占满一行。
- 地址独立于参数区，继续保留地图与复制/导航交互。
- 商家资料入口在地址之后；现有“资料已完善”准入规则不变。
- 交易提醒移到同类推荐之后，并降低卡片视觉权重，避免干扰联系决策。

### 文案

- 页面标题、管理标题、审核说明、下架确认、收藏反馈、相关推荐空态等统一复用 `resourceNoun`（“供应”或“需求”）和 `resourceNounPlural`（“供需信息”）。
- 已成交状态继续使用中性文案“该供需已完成”。

## 数据与兼容性

本次直接消费现有详情响应字段，不增加 API 请求：

- `direction`：供需方向；
- `typeName`、`typeCode`：二级类型；
- `title`：自动生成摘要；
- `category`、`priceText`、`quantityText`：首屏回退与关键事实；
- `attributeItems`：详细参数；
- `description`、`images`、`tags`、`merchant`：沿用现有逻辑。

历史数据缺少 `direction` 时，保留现有基于 `typeCode` 的需求类型兼容判断。

## 验收标准

1. 不增加发布标题输入框，发布流程与字段校验保持不变。
2. 任一详情页首屏均可展示供需方向、类型和自动摘要；图片缺失时亦成立。
3. 有价格或数量摘要时，首屏展示对应事实；缺失时不显示占位。
4. 需求详情中不出现“供应管理”“下架供应”“暂无同类供应”等固定供应口径。
5. 长参数在移动端以整行展示，短参数仍保持双列密度。
6. 商家资料入口的展示条件保持“有商家 ID 且资料状态为 `completed`”。
7. 资源详情页相关前端测试覆盖首屏摘要、无图摘要、动态文案、参数跨度与原有联系/管理行为。
