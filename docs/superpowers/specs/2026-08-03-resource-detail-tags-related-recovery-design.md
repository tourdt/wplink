# 供需详情标签与同类推荐恢复设计

## 背景

当前详情页出现两个用户可见问题：

1. 标签展示模型会过滤与 `typeName`、`category` 相同或被其包含的标签，但页面首行只展示 `typeName`，造成部分有效信息被隐藏；多数童装供需类型又没有发布标签配置，旧数据最终没有任何展示标签。
2. 同类推荐只在公开详情加载；从“我的发布”进入时明确跳过。公开详情又只查完全相同的 `typeCode`，且浏览统计失败会阻断后续推荐请求，因此推荐区经常整体消失。

## 目标

- 详情页在存在有效业务信息时展示有意义的标签，不制造与可见类型完全重复的标签。
- 旧资源即使没有用户标签，也能用分类提供一个稳定、可理解的标签兜底。
- 公开详情和本人详情都能看到公开发布的类似供需。
- 推荐数据独立失败，不影响详情主体、浏览统计、收藏或商家资料。
- 推荐规则由后端集中维护，前端不拼装业务排序。

## 方案比较

### 方案 A：展示标签兜底 + 独立推荐接口（采用）

后端生成 `presentation.tags`，并提供资源相关推荐接口。推荐接口按业务相似度分层补足，前端只渲染返回结果。

优点是规则集中、两种详情入口一致、可独立容错，后续增加城市、时效或质量权重时不需要改页面。代价是增加一个只读接口及查询逻辑。

### 方案 B：前端复用列表接口连续回退

前端依次按类型、分类、方向发起列表请求并去重。改动较少，但请求次数多、排序规则散落在页面，其他端需要重复实现。

### 方案 C：继续只查完全相同类型

仅放开本人详情并增加空态。实现最小，但数据量较少时仍然经常没有推荐，不能解决核心问题。

## 标签展示规则

后端继续保留原始 `tags`，并单独生成展示用 `presentation.tags`：

1. 对标签执行首尾空白清理，过滤空值并稳定去重。
2. 仅过滤与页面实际可见 `typeName` 完全相同的标签。
3. 不再因为标签与 `category` 相同或被 `typeName`、`category` 包含而删除，避免隐藏页面未直接展示的信息。
4. 如果过滤后没有特征标签，且 `category` 非空并且不等于 `typeName`，返回一个分类兜底标签。
5. 原始详情 `tags` 保持不变，用于编辑、再发类似及其他业务场景。

发布配置方面，为当前缺少 `tagOptions` 的活跃供需类型补充符合业务语义的可选特征标签。该配置只影响后续发布与编辑；旧数据由分类兜底保证详情不空，不批量伪造历史用户选择。

## 同类推荐接口

新增只读接口：

`GET /api/v1/resources/:resourceId/related?pageSize=3`

接口只返回已公开发布、商家状态有效的资源，并始终排除当前资源。结果按以下优先级稳定补足并去重：

1. 相同 `typeCode`；
2. 相同业务分组 `displayTemplate.group.code`；
3. 相同 `direction`。

同一优先级沿用公开资源列表的有效排序。默认返回 3 条，最大 6 条。当前资源即使是本人通过私有详情查看，推荐结果仍只包含公开资源。

## 前端数据流与容错

- 详情主体加载成功后，独立调用同类推荐接口，不再受 `isOwnResource` 限制。
- 商家资料、浏览统计、收藏状态、同类推荐分别执行和容错；其中一个辅助请求失败不得阻断其他请求。
- 推荐请求失败或返回空数组时隐藏推荐区，不弹出全局错误提示，不影响用户继续查看详情。
- 有推荐数据时沿用现有 `ResourceList` 的 `feed` 样式和“查看更多”入口。
- 进入另一条相关资源详情时清理上一条推荐状态，避免短暂显示旧数据。

## 测试与验收

### 后端

- 标签测试覆盖：完全等于类型时过滤、分类相同但类型不同则保留、包含关系不误删、无特征标签时分类兜底、原始标签不变。
- 推荐逻辑测试覆盖：排除当前资源、仅返回公开有效资源、同类型优先、同分组补足、同方向兜底、稳定去重及数量上限。
- API 契约测试覆盖路由参数与响应结构。
- 配置测试确认所有活跃供需类型均具有合法的 `tagOptions`。

### 小程序

- API 测试覆盖相关资源接口及空列表默认值。
- 页面测试覆盖公开详情与本人详情都会加载推荐。
- 测试证明浏览统计或收藏请求失败不会阻断推荐加载。
- 空推荐不显示区域，有数据时继续使用统一供需列表卡片。

### 验收示例

- 类型“求购尾货”、分类“童装”、原始标签为空时，详情展示“童装”。
- 类型“求购尾货”、标签“急采、可接受断码”时，两个特征标签均保留。
- 从“我的发布”打开需求详情，也能看到最多 3 条公开同类供需。
- 同类型不足 3 条时，能够从同业务分组及同供需方向补足。
