# 新手成长权益活动设计

## 背景

平台冷启动阶段需要快速增加真实资源供给，同时避免用“完善商家名片”作为主要门槛。前台资源详情已支持分享到微信群和朋友圈，并能生成资源分享封面；下一步需要把分享和发布行为转化为可运营的增长权益。

当前系统已有权益承载能力：

- `merchant_entitlements`：保存发布次数、刷新次数、置顶券等权益批次。
- `merchant_entitlement_usage_records`：保存发布、刷新、置顶等权益使用流水。
- `resource_contact_events`：保存资源分享、电话、微信等联系行为事件。
- 资源发布时会扣减 `publish_quota`，资源刷新时会扣减 `refresh_quota`。

现有普通用户默认额度仍按商家名片状态区分。新方案需要把冷启动赠送逻辑从“名片完善程度”转为“新手成长活动”，奖励真实发布、有效分享和有效邀请。

## 目标

1. 新用户首次进入后立即获得少量发布次数，能马上发布资源。
2. 弱化商家名片，不再用“完善商家名片”作为主要奖励条件。
3. 奖励真实行为：资源审核通过、分享带来有效浏览或联系、邀请同行完成真实发布。
4. 奖励数值、门槛、有效期、适用范围和发放上限可由后台随时调整。
5. 活动支持暂停、恢复、结束和停用；停用后立即停止新奖励发放。
6. 已发放权益按发放时快照和有效期继续使用，避免运营策略变化影响历史用户。
7. 后端保留发放记录、幂等键和运营日志，便于排查刷量、重复发放和配置误操作。

## 非目标

1. 本阶段不实现复杂任务中心或积分商城。
2. 本阶段不把分享奖励做成立即到账的无条件转发奖励。
3. 本阶段不删除商家资料、发布者资料或历史认证能力。
4. 本阶段不实现多层级代理分销、现金红包或提现。
5. 本阶段不替代 VIP 套餐、次数包和人工权益发放能力。

## 方案选择

采用“配置化活动 + 事件触发 + 权益发放记录 + 复用现有权益表”的方案。

理由：

- 冷启动活动需要频繁调整数值，硬编码在注册、发布或分享逻辑里会导致后续改动风险高。
- `merchant_entitlements` 已经能表达发布次数、刷新次数和置顶券余额，不需要再建一套余额账户。
- 新增活动表和发放记录表后，可以清楚区分运营增长权益、VIP 权益、购买权益和人工补发权益。
- 活动状态可以作为全局开关，满足“过一段时间随时停用”的运营要求。

不采用“完善商家名片赠送更多额度”的方案。商家资料可以继续作为信任信息和联系方式承载，但不再作为新用户获取发布次数的主路径。

## 活动模型

新增增长活动配置，建议命名为 `growth_campaigns`。

核心字段：

| 字段 | 说明 |
| --- | --- |
| `code` | 活动编码，例如 `starter_growth_2026_q3` |
| `name` | 活动名称，例如“新手成长权益活动” |
| `status` | `draft`、`active`、`paused`、`ended`、`disabled` |
| `starts_at` | 活动开始时间 |
| `ends_at` | 活动结束时间，可为空 |
| `city_scope` | 适用城市，空数组表示全站 |
| `user_scope` | 适用用户类型，默认普通用户和 VIP 用户都可参与 |
| `total_reward_limit` | 活动总发放上限，可为空 |
| `daily_reward_limit` | 活动每日发放上限，可为空 |
| `config_snapshot` | 活动级配置快照，便于扩展前端文案和风控参数 |
| `created_by` | 创建管理员 |
| `updated_by` | 最近更新管理员 |

状态含义：

| 状态 | 含义 |
| --- | --- |
| `draft` | 草稿，不参与规则匹配 |
| `active` | 启用，事件进入后可匹配并发放奖励 |
| `paused` | 暂停，临时停止新奖励发放，可恢复 |
| `ended` | 已结束，不再发新奖励，通常由结束时间或运营操作触发 |
| `disabled` | 已停用，紧急或永久关闭，需要运营日志记录原因 |

## 规则模型

新增活动规则配置，建议命名为 `growth_campaign_rules`。

核心字段：

| 字段 | 说明 |
| --- | --- |
| `campaign_code` | 所属活动 |
| `rule_code` | 规则编码，例如 `first_login_publish_quota` |
| `trigger_event` | 触发事件 |
| `status` | `active` 或 `inactive` |
| `priority` | 匹配优先级 |
| `conditions` | JSON 条件配置 |
| `reward_type` | `publish_quota`、`refresh_quota`、`top_voucher` |
| `reward_amount` | 发放数量 |
| `valid_days` | 权益有效天数 |
| `per_user_limit` | 每用户总发放上限 |
| `per_user_daily_limit` | 每用户每日发放上限 |
| `per_resource_daily_limit` | 每资源每日发放上限 |
| `description` | 运营说明 |

支持的触发事件：

| 事件 | 说明 |
| --- | --- |
| `user_first_login` | 新用户首次登录 |
| `resource_first_approved` | 用户首条资源审核通过 |
| `resource_approved_count_reached` | 一段时间内审核通过资源数量达到门槛 |
| `resource_share_effective_view` | 分享带来有效浏览 |
| `resource_share_effective_contact` | 分享带来有效联系 |
| `invitee_first_resource_approved` | 被邀请人首条资源审核通过 |

## 推荐初始规则

| 规则 | 触发条件 | 奖励 | 有效期 | 上限 |
| --- | --- | ---: | --- | --- |
| 首次登录 | 用户首次登录且活动启用 | 发布次数 +3 | 30 天 | 每用户一次 |
| 首条审核通过 | 用户首条资源审核通过 | 发布次数 +5 | 30 天 | 每用户一次 |
| 连续优质发布 | 30 天内 3 条资源审核通过，且无投诉 | 发布次数 +5、刷新次数 +3 | 30 天 | 每用户一次 |
| 分享有效浏览 | 单条资源分享带来 5 个有效浏览 | 刷新次数 +1 | 15 天 | 每资源每日 1 次，每用户每日 3 次 |
| 分享有效联系 | 分享带来电话点击或微信复制 | 刷新次数 +1 | 15 天 | 每用户每日 3 次 |
| 邀请成功 | 被邀请用户首条资源审核通过 | 邀请双方各发布次数 +5 | 30 天 | 邀请人每月最多 50 次，首期默认不启用 |

有效浏览判断建议：

- 访问用户不能是资源发布者本人。
- 同一用户、同一设备或同一分享来源在 24 小时内只计一次。
- 资源必须处于已发布状态。
- 异常频率、黑名单设备或风险用户不计入奖励门槛。

有效联系判断建议：

- `phone` 和 `wechat` 属于有效联系。
- `share` 只作为分享动作记录，不直接发放发布次数。
- `merchant_profile` 或发布者主页访问可以计入分析数据，但不作为核心奖励条件。

邀请奖励依赖邀请关系和归因链路。当前阶段先在活动规则中预留 `invitee_first_resource_approved`，默认保持 `inactive`，等邀请关系表和来源归因稳定后再启用。

## 权益发放记录

新增权益发放记录，建议命名为 `growth_reward_grants`。

核心字段：

| 字段 | 说明 |
| --- | --- |
| `campaign_code` | 活动编码 |
| `rule_code` | 规则编码 |
| `merchant_id` | 获得权益的商家 |
| `user_id` | 触发用户，可为空 |
| `resource_id` | 关联资源，可为空 |
| `event_id` | 关联事件，可为空 |
| `idempotency_key` | 幂等键 |
| `reward_type` | 奖励类型 |
| `reward_amount` | 奖励数量 |
| `valid_days` | 发放时有效期快照 |
| `entitlement_id` | 写入 `merchant_entitlements` 后的权益批次 |
| `status` | `granted`、`skipped`、`failed`、`revoked` |
| `reason` | 发放、跳过或失败原因 |
| `snapshot` | 活动、规则、条件和风控判断快照 |

幂等键规则：

```text
campaign_code + rule_code + merchant_id + resource_id/event_id/period_key
```

示例：

- 首次登录：`starter_growth_2026_q3:first_login_publish_quota:merchant_1`
- 首条审核通过：`starter_growth_2026_q3:first_resource_approved:merchant_1:resource_9`
- 分享有效浏览：`starter_growth_2026_q3:share_view_refresh:merchant_1:resource_9:2026-07-10`
- 邀请成功：`starter_growth_2026_q3:invitee_first_resource_approved:inviter_1:invitee_2`

## 发放流程

1. 业务动作产生事件，例如登录、资源审核通过、联系事件写入。
2. 增长权益服务读取当前 `active` 活动和启用规则。
3. 校验活动时间、城市范围、用户范围、规则状态和风控条件。
4. 生成幂等键，检查 `growth_reward_grants` 是否已发放或已跳过。
5. 检查单用户、单资源、每日、每月和活动总上限。
6. 事务内写入 `merchant_entitlements`，`source_type` 使用 `growth_campaign`。
7. 事务内写入 `growth_reward_grants`，保存规则快照和发放结果。
8. 用户侧在权益页和发布入口看到新增余额。

如果发放失败：

- 后端记录包含活动编码、规则编码、商家 ID、资源 ID、事件 ID 和根因的错误日志。
- 前台不暴露数据库错误；可在需要展示时提示“成长权益正在处理中，请稍后查看”。
- 后台支持按失败记录重试，重试仍使用相同幂等键。

## 停用与调整策略

运营可以随时调整规则数值。调整后只影响新触发事件，不修改历史 `growth_reward_grants` 和已发放 `merchant_entitlements`。

停用语义：

| 操作 | 影响 |
| --- | --- |
| 暂停活动 | 立即停止新奖励发放，历史权益继续可用，可恢复 |
| 恢复活动 | 从恢复时间开始继续匹配新事件，不补发暂停期间事件 |
| 结束活动 | 停止新奖励发放，用于自然到期或阶段结束 |
| 停用活动 | 紧急关闭，后台隐藏前台活动提示，需要记录停用原因 |

已发放权益处理：

- 正常停用不回收已发权益。
- 已发权益按发放时的 `valid_days` 到期。
- 如发现刷量，可由后台人工将对应发放记录标记为 `revoked`，并调整未使用余额。
- 已经被用户消费的权益不自动追扣，避免引发资源状态和用户体验问题。

## 后台能力

新增“增长活动”后台页面。

页面能力：

1. 活动列表：查看活动编码、状态、时间范围、发放总量和最近更新时间。
2. 活动编辑：维护名称、时间、适用城市、总预算、日预算和活动状态。
3. 规则列表：维护触发事件、奖励类型、奖励数值、有效期、门槛和上限。
4. 一键暂停：将活动从 `active` 改为 `paused`。
5. 一键停用：将活动改为 `disabled`，必须填写原因。
6. 发放记录：按活动、规则、商家、资源、状态筛选发放流水。
7. 操作日志：记录配置前后差异、管理员和操作时间。

后台校验：

- 奖励数量必须大于 0。
- 有效期必须大于 0。
- 结束时间必须晚于开始时间。
- 活动停用后不能直接编辑为启用，需要先复制或重新启用并记录原因。
- 分享类奖励必须配置门槛和上限，不能配置为无条件分享即发放。

## 小程序呈现

小程序不做复杂任务中心，先在关键路径做轻提示：

1. “我的”页面和权益页展示发布次数、刷新次数和即将过期权益。
2. 发布页在额度不足时提示“发布次数不足，可通过发布优质资源、有效分享或开通 VIP 获取更多次数”。
3. 首条资源提交成功后提示“审核通过后可获得新手发布权益”。
4. 资源分享按钮保留当前分享封面能力，文案使用“分享带来真实浏览，可获得刷新权益”。
5. 不出现“完善商家名片得更多发布次数”的主路径文案。

## 与 VIP 和人工发放的关系

增长活动权益只负责冷启动激励：

- `source_type = growth_campaign`：增长活动发放。
- `source_type = vip`：VIP 周期权益。
- `source_type = vip_addon`：次数包购买权益。
- `source_type = manual`：后台人工补发。

扣减发布次数和刷新次数时继续按权益批次有效期排序，优先消耗更早过期的有效批次。活动停用不影响 VIP、次数包和人工发放。

## 风控与数据指标

基础风控：

- 自己访问自己的资源不计入分享有效浏览。
- 同一访问主体 24 小时内重复访问同一资源只计一次。
- 被投诉、被封禁或资源被驳回的用户不发放新增奖励。
- 分享浏览奖励不发发布次数，只发刷新次数，降低刷发布额度风险。
- 邀请奖励必须等被邀请人首条资源审核通过后发放。

复盘指标：

- 活动发放人数、发放次数、发放权益总量。
- 新用户首发率、首条审核通过率、资源驳回率。
- 分享访问数、有效浏览数、有效联系数。
- 发布次数使用率、刷新次数使用率。
- 通过活动产生的资源数量和联系行为数量。
- 投诉率、异常设备数、异常重复访问数。

## 错误处理

- 活动未启用：静默跳过，不提示用户。
- 规则未启用：静默跳过，不提示用户。
- 重复事件：幂等跳过，记录 `skipped`。
- 达到上限：记录 `skipped`，原因保存为 `limit_reached`。
- 权益写入失败：记录错误日志，发放记录保存为 `failed`。
- 用户侧余额读取失败：提示“权益信息暂时不可用，请稍后重试”。

后端日志必须包含活动编码、规则编码、商家 ID、资源 ID、事件 ID 和错误根因；前端错误不能暴露 SQL、表名或内部异常。

## 测试策略

后端测试：

- 活动未启用、暂停、结束、停用时不发放奖励。
- 首次登录只发放一次发布次数。
- 首条资源审核通过只发放一次发布次数。
- 分享有效浏览达到门槛后发放刷新次数。
- 分享有效联系发放刷新次数，并受每日上限限制。
- 邀请成功后双方发放发布次数。
- 幂等键重复时不重复写入权益。
- 调整规则数值后，历史发放记录和已发权益不变化。
- 活动停用后新事件不发放，旧权益仍可使用。

小程序测试：

- 分享封面和分享路径保持可用。
- 发布页额度不足提示不再强调商家名片。
- 权益页能展示活动发放的发布次数和刷新次数。
- 活动停用后前台不展示活动引导文案。

迁移测试：

- 新增活动、规则、发放记录表的 up/down 迁移完整。
- `growth_reward_grants.idempotency_key` 唯一约束生效。
- `merchant_entitlements.source_type = growth_campaign` 可正常参与余额查询和扣减。

## 实施边界

第一阶段只实现新手成长权益活动的配置、发放和停用能力，不实现复杂任务中心。前端只在发布、分享和权益页给轻提示。

需要优先替换现有普通用户按名片状态自动发月度权益的逻辑：普通用户基础发布次数应来自增长活动或普通权益配置，不能继续因为“完善名片”自动获得更多发布次数。
